## 方法与注意事项

1. **认证**：票面给的 guest-session 路径不够——生产模式 Lurk Wall（app.ts）下 guest 会话 `userId=null`，`optionalAuth` 找不到 User，除 `/channels` 等公开只读端点外一律 401。实际做法：用既有用户的 refreshToken 走公开端点 `POST /api/v1/auth/refresh` 换了 Admin token，种进 localStorage `auth-storage`（前端 axios 拦截器从 zustand persist 取 Bearer，cookie 无效）。
2. **并行改动干扰（重要）**：盘点期间有另一会话在改前端——vite HMR 日志 15:35 / 15:38 / 15:43(+0800) 触及 `ChannelDetailPage.tsx`、`PMOPage.tsx`、`ProjectDetailPage.tsx`、`AgentDashboardPage.tsx`、`proposalCardConfigs.tsx`、`index.css` 等。截图反映的是**拍摄时刻的工作树状态**，不保证等于 master HEAD；频道工作区/PMO 相关页若与 master 有出入，以本说明为准。HMR 全量刷新也是拍摄中多次"加载中…"残影的来源（已全部重拍确认终态）。
3. headless 浏览器缺 emoji 字体，侧边栏图标显示为 □——**这是截图环境伪影，不是产品问题**。
4. 各页面真实数据选用：频道 = #系统（1327 条消息）；PMO 项目 = PMO-1（proj_1787122016333_havci58）；WU = 09cd2207（in_review，分析需求）；Agent = e2e-analyst（d6a32872）。

## 全局发现

- **base 字号 12.5px 等宽字体**：实测 `body` computed `font-size: 12.5px; font-family: ui-monospace, ...`。全站正文、表格、卡片全部 12.5px 等宽，中文在等宽字体下字面偏窄，长文本（监控告警、知识条目）可读性明显吃力。✔ 与已知背景一致。
- **布局宽度三种范式并存**（实测，按页）：
  - 居中极窄栏：频道列表 max-w-lg = 512px；
  - 居中中栏：频道工作区消息流/输入框 760px（≥1440px 放宽到 1000px，见 mission-control.css:215/636/943 的 `@media (min-width: 1440px)`）；PMO 项目详情约 975px 居中；
  - 左对齐固定栏：WorkUnit/Agent/监控/知识库/设置 ≈ 1024px 左对齐（右侧大片空白）；
  - 全宽：PMO 列表、阅览室（内容从侧栏右缘一直拉到屏幕右缘）。
  四种宽度策略在一个 App 里混用，页面间跳转时内容落点忽左忽中忽满，**割裂感的结构性来源**。
- **加载状态脆弱**：页面普遍以纯文本"加载中…"占位，且 SSE 重连/数据 refetch 时会整页退回加载态（盘点中多次遇到已加载页面闪回"加载中…"）。

## 分页盘点

### 1. /channels 频道列表 — `channels-1920.png` / `channels-1440.png`

- 宽度：max-w-lg（512px）居中（ChannelListPage.tsx:41），✔ 与已知背景一致。
- 1920 下主区 ~1440px 宽，内容只占中间 512px；右侧另有 "AGENT 状态" 竖栏常驻（本环境无运行实例，长期只有"加载中…"/空态），等于左右两边都是死空间。
- 列表行信息极少：频道名 + 类型两个字，无未读数、无最后消息时间、无成员摘要——3 个频道也要点进去才知道有没有事。
- 「快速开始」指引卡挂在列表下方，常驻不消失（已有 3 频道、1300+ 消息的老用户也天天看新手引导）。

### 2. /channels/:id 频道工作区 — `channel-detail-1920.png` / `channel-detail-1440.png`，@弹框证据 `channel-mention-1920.png`

- 宽度：三栏（频道列 ~225px + 消息列 + 右侧随宽度出现）。消息流 `.mc-stream-inner` 与输入框 `.mc-inputbar-inner` max-width 760px，**≥1440px 放宽至 1000px**（mission-control.css:215,636,855，断点在 943 行）。实测：1920 下 inner=1000px（消息列总宽 1440px，两侧各空 ~220px）；1440 下 inner=932px（受可用列宽挤压，未到 1000）。已知背景"760px 居中、≥1440 才 1000"✔ 属实，且 1920 大屏割裂感明确：消息文字居中一窄条，左右深色空海。
- **系统频道消息视觉重心偏右**：#系统 的 Monitor 告警消息呈右对齐排布（贴 inner 右缘），左侧大片空白，扫读时视线要跳到右边找行首。

- 顶栏 `成员 All 默认工程：无` 等元信息一行平铺到右缘，与 1000px 内容列不对齐。
- 数据层观察（非 UI 本身但影响观感）：#系统 1327 条消息里绝大多数是重复的 `[CRITICAL] [Monitor] pool_stagnation/review_stagnation` 滞留告警，同一内容每小时重发——频道作为"信息面"已被告警洪水淹没，截图里一屏全是同一条告警。

## 补充新发现（超出已知背景）

1. 全站四种宽度策略混用（512 居中 / 760-1000 居中 / 1024 左对齐 / 全宽），页面间内容落点漂移——重构时建议先定全局栅格。
2. 频道工作区系统消息右对齐，视觉重心反直觉。
3. 告警洪水同时淹没 #系统 频道、监控页、知识库三个面（同源 Monitor 数据无聚合无去重）。
4. 知识库直出存储层原始 JSON/告警原文。
5. 加载态脆弱：SSE 重连即整页退回"加载中…"。
6. PMO 项目页三处进度表达互相矛盾（流转条 vs 管道 100% vs 进展卡 0%）。
7. 列表页混入行级人闸操作（/workunits 审查中行的通过/拒绝按钮）。
