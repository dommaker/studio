# 任务规划与 SDD 编写

把设计 Spec 转化为可执行的 SDD 三层文档。探索代码、定义接口、规划测试。

---

## 集成

上游：**spec-review-skill**（PASS 的设计 Spec）或 **design-analyst**（需求已明确时直跳）。
产出：SDD 三层文档 或 轻量 PLAN。
下游：**sdd-review-skill**（审查 SDD 质量）或 **tdd-implement**（轻量 PLAN 直跳）。

---

## 硬门禁

<HARD-GATE>
涉及多模块/有设计空间/需依赖分析时，必须产出完整 SDD。单一改动/接口已定时，轻量 PLAN 即可。判断在 Step ① 完成。
</HARD-GATE>

---

## 反模式：常见借口

| 借口 | 反驳 |
|------|------|
| "Spec 已经够详细了" | Spec 是高层设计，SDD 是实现指导。Spec 没有文件映射和接口定义。 |
| "代码结构我熟，不用探索" | 你熟悉的可能是旧代码。探索 = 验证假设，不是学习。 |
| "文件映射太细了" | 文件映射是 tdd-implement 的输入。没有映射 = 实现时现找文件 = 浪费。 |
| "依赖分析没必要" | 依赖分析决定并行还是串行。跳过 = 全部串行 = 慢。 |
| "测试规划和实现一起做" | 测试规划在 SDD 里，实现在 tdd-implement 里。混在一起 = 先实现后测试。 |
| "源项目合并了所以覆盖了" | 合并 ≠ 覆盖。多个源项目可能来自同一文件/模块，但职责不同（如一个提取算法 pattern，另一个文档化工程经验），合并时必须显式列出被合并的源项目并确认内容完整。 |
| "这个项不好提取所以跳过" | "不好提取" ≠ "不需要"。无法代码化的经验仍然是合法产出（文档化/知识条目）。不提取就随源文件消亡。 |

**危险信号**：
- 跳过代码探索直接写 SDD
- 文件映射只写模块名不写具体文件
- 接口定义用"待定"占位
- 没有代码依赖分析
- 源文档有 N 个项目但 SDD 只有 < N 个 AC 且无排除决策（源覆盖缺口）

## 执行流程

### ① 读取输入 + 快速退出判断

从输入（设计 Spec 或用户描述）提取：
- 目标和约束
- 方案选定
- AC 定义
- 实施路径
- **风险评估**（从 spec 继承，未标注 → 默认为 safe）

**源项目枚举**（当输入是分析文档/spec 且含多个可操作项时）：

逐项列出源文档中所有需要交付的工作项，标注每项的产出类型（代码/文档/配置/测试等，按实际场景确定）。

输出"源项目清单"表格：
```
| # | 源项目 | 产出类型 | SDD AC |
|---|--------|---------|--------|
| 1 | xxx    | 代码提取 | AC-1   |
| 2 | yyy    | 经验文档化 | AC-4   |
```

此表贯穿后续所有步骤。任何项从"源项目"变为"排除"必须有显式决策和理由。

**快速退出检查**（基于已读输入判断）：

```
if 改动单一 && 接口已定（无设计空间）:
    产出轻量 PLAN（AC 列表 + 文件映射 + 测试规划，不要求三层文档格式）
    输出："改动单一，跳过完整 SDD → 直接实现"
    → invoke tdd-implement（以轻量 PLAN 为输入）
    终止本 Skill
```

继续执行 = 涉及多模块/接口未定/需依赖分析。

### ② 代码探索

识别涉及的模块，**并行探索**：

```
对每个独立模块：
  - 扫描目录结构
  - 读取关键文件（入口、接口、类型定义）
  - 识别调用链和依赖关系

独立模块 → parallel-execution 并行探索
有依赖的模块 → 按依赖顺序串行探索
```

探索产出：
- 每个模块的文件清单
- 现有接口和类型定义
- 调用链和依赖关系

### ③ 编写 requirement.md

```yaml
---
status: draft
version: "1.0"
# pmoNumber: "PM-NNN"  # 可选：关联 PMO 编号，由上游传入或手动填入
---
```

内容：
- AC Group 定义（按功能模块分组）
- 每个 AC 包含：触发条件、预期行为、边界情况、不做项
- AC → 文件映射（哪些 AC 涉及哪些文件）
- **源项目追溯**：每个 AC Group 头部标注 `covers: [源项目编号]`，标明该 AC 覆盖源清单中的哪些项。一个 AC 可覆盖多个源项目，但必须显式列出，不得隐含

### ④ 编写 design.md

```yaml
---
status: draft
version: "1.0"
---
```

内容：
- 文件映射表（AC → 文件路径 → 改动类型）
- 接口定义（函数签名、参数类型、返回值）
- 代码依赖图（文件间的依赖关系）
- 模块边界和约束

### ⑤ 编写 task.md

```yaml
---
status: draft
version: "1.0"
---
```

内容：
- 契约测试规划（每个 AC → 测试文件 → 测试用例）
- 执行顺序（依赖分析结果：并行/串行）
- 里程碑节点
- **每个 Phase 标注风险等级**（继承 spec）：`[safe]` / `[breaking]` / `[destructive]`
- `[destructive]` Phase 在概要中醒目标注，供 tdd-implement 兜底确认
- **Implementation Readiness 评估**：task.md 末尾添加 `## Implementation Readiness` 节，格式：
  ```
  implementationReady: true/false

  | # | 条件 | 满足 | 证据 |
  |---|------|------|------|
  | 1 | design.md 有精确 file:line 引用 | ✅/❌ | ... |
  | 2 | 非平凡变更有 before/after 代码块 | ✅/❌ | ... |
  | 3 | 消费方覆盖（谁 import 受影响文件） | ✅/❌ | ... |
  | 4 | 测试断言具体（不只是"测试通过"） | ✅/❌ | ... |
  | 5 | 接口定义完整（签名+参数+返回值） | ✅/❌ | ... |
  ```
  - 5 条全满足 -> `implementationReady: true` -> tdd-implement 使用 CLI 轻量模型设置
  - 任一不满足 -> `implementationReady: false` + 标注缺口 -> tdd-implement 使用 CLI 默认模型设置

### ⑥ 三层一致性检查

```
Requirement.AC ↔ Design.文件映射 ↔ Task.契约测试
```

每层结论必须可追溯到上层，可被下层验证。

---

## 依赖分析

```
对 design.md 中的文件映射：
  提取每个文件的 imports/调用关系
  构建文件依赖图（DAG）
  标注：哪些文件独立（可并行）、哪些有依赖（需串行）
```

产出写入 task.md 的"执行顺序"节，供 tdd-implement 的 parallel-execution 使用。

---

## 自检

自检修复最多 3 轮。超过 3 轮仍未全部通过 → 停下报告，不继续循环。不 invoke 下游。

| # | 检查项 | 通过标准 | 不通过动作 |
|---|--------|---------|-----------|
| 1 | 三层完整 | requirement.md + design.md + task.md 都存在 | 补全缺失层 |
| 2 | AC 可测试 | 每条 AC 有明确 pass/fail 条件 | 重写为可验证格式 |
| 3 | 文件映射具体 | 具体文件路径，不是模块名 | 补充具体路径 |
| 4 | 接口定义完整 | 函数签名 + 参数类型 + 返回值 | 补充缺失定义 |
| 5 | 依赖分析 | 文件 DAG 存在，标注并行/串行 | 补充依赖分析 |
| 6 | 契约测试规划 | 每个 AC 有对应测试文件和用例 | 补充测试规划 |
| 7 | 三层一致 | AC ↔ 文件映射 ↔ 测试对齐 | 修复断裂点 |
| 8 | 无占位符 | 无 "TBD"/"TODO"/"待定" | 补全后再提交 |
| 9 | 源覆盖 | 源项目清单每项有对应 AC 或显式排除决策（含理由） | 补充缺失 AC 或补排除决策 |
| 10 | 风险继承 | task.md 每个 Phase 标注风险等级，与 spec 一致 | 补充风险标注 |
| 11 | 就绪度评估 | task.md 有 `implementationReady` 判定 + 5 条件检查清单 | 补就绪度评估 |
| 12 | 就绪度证据 | ready=true 时每条条件有具体证据；ready=false 时缺口已标注 | 补证据或标注缺口 |

全部通过后进入终端状态。

---

## 终端状态

<HARD-GATE>
SDD 产出后必须进入质量审查，不得跳过直接实现。审查是硬门禁，不是可选项。

SDD 含 `[destructive]` Phase → 呈现破坏性操作清单 → **等用户确认** → 再 invoke 下游。

SDD 无 destructive → 呈现概要 → 等用户确认 → 再 invoke 下游。
</HARD-GATE>

自检全部通过后：

1. **呈现概要**：总结 Phase 划分、风险标注、文件变更范围。等待用户确认。
2. 用户确认后：

- 完整 SDD（多文件、需审查）→ **invoke sdd-review-skill**
- 轻量 PLAN（1-2 文件、方案明确）→ **invoke tdd-implement**

路由由产出类型自动判定，用户确认后 invoke。
