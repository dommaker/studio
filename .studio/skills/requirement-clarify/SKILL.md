# 需求澄清与设计（位1）

位1 主方法论。把模糊的一句话需求澄清成可验收的结构化结论；有设计空间时展开方案对比与详细设计，产出 spec 落业务仓 `.studio/specs/`（冻结正本），过位2 就绪度质量门后路由拆单。

---

## 集成

上游：用户原始需求（频道消息 / @mention / 直接对话）。
产出：澄清结论；有设计空间时追加 spec（`.studio/specs/<slug>.md`）。
下游：**to-tickets**（spec 过位2 质量门后拆单）。

澄清/设计过程中固化的领域术语 → 业务仓 `.studio/CONTEXT.md` 词条；架构级决策 → `.studio/adr/`。

---

## 触发条件

满足任一即触发本 skill：

- 需求表述模糊，无法直接写出可验证的验收标准（"帮我优化一下系统"、"能不能做个管理功能"）
- 缺关键信息四要素之一：**目标**（为什么做）、**边界**（做什么/不做什么）、**约束**（技术/时间/兼容性限制）、**验收**（怎么算做完）

---

## 硬门禁

<HARD-GATE>
每轮只问最关键的 1-3 个问题，禁止一次性抛问卷式清单。每个问题必须附带建议答案供用户确认/修改，禁止开放式提问（"你想要什么？"是违禁句式）。

澄清结论未固化（结构化输出未产出）前，不得进入设计；spec 未过位2 质量门前，不得 invoke to-tickets。
</HARD-GATE>

---

## 沟通规则（贯穿全程）

- **事实自行查证**：能通过 grep/read/ls 查证的（文件是否存在、函数是否导出、接口是否定义）自行查证，不问用户
- **决策交给用户**：事实查证清楚后，怎么决策由用户确认。每个问题附推荐答案 + 理由
- **未达成共识前不执行**：用户确认前不进入下一阶段、不调用下游 skill

---

## 阶段一：澄清

### 问题分级

| 级别 | 含义 | 处理方式 |
|------|------|---------|
| 必须澄清 | 阻塞性缺口：缺了无法定义验收标准（目标不明、核心边界不明） | 提问，等回答 |
| 可以默认 | 有合理行业/项目默认值的缺口（技术栈、非核心边界、性能指标） | **给出默认值继续**，在结论中标注"默认假设"，用户可事后纠正 |

每轮问题 = 从"必须澄清"里挑最关键的 1-3 个。"可以默认"项不提问，直接写进假设清单。

### 提问格式

```
Q1: 这个功能主要给谁用？
    建议答案：内部运营同学（约 20 人），不对外开放。
    → 确认请回"对"，否则直接改。
```

### 停止条件

- 信息足够写出**可验收**的需求（四要素齐全，每条验收标准可判 pass/fail）
- 用户明确说"直接做"/"别问了"/"按你说的来" → 用当前信息 + 默认假设直接固化

追问轮次上限 5 轮。超过仍缺关键信息 → 列出剩余缺口 + 建议默认值，请用户一次性裁决。

### 固化：澄清结论

```markdown
## 澄清结论

**目标**：<为什么做，解决什么问题>
**范围**：
- 做：<in-scope 清单>
- 不做：<out-of-scope 清单>
**约束**：<技术/时间/兼容性约束，无则写"无显式约束">
**验收标准**：
1. <可判 pass/fail 的 AC>
2. ...
**工程归属**：<目标仓库/工作区>
**默认假设**（未经用户确认，可纠正）：
- <假设 1>
```

**快速退出**：目标明确 && 约束清晰 && 方案唯一（无设计空间）→ 跳过阶段二，澄清结论直接作 to-tickets 输入（小需求跳步零负担）。范围大（2+ 独立 AC 组 / 跨 2+ 架构层 / 引入 2+ 新概念）则不跳步。

## 阶段二：设计（有设计空间时）

### ① 第一性分析

从本质问题出发，不从当前代码推导：根本原因是什么？有哪些解决路径？每条路径的 trade-off？

**验证要求**：每条事实性声明必须有验证证据。先 grep/read 收集证据，再写结论。禁止从结构代理推导运行时行为（"表有字段 → 能力已实现"为无效推导）。产出含**声明-证据对照表**：

| 声明 | 验证方式 | 证据摘要 |
|------|---------|---------|
| "X 能力已覆盖" | grep 消费方代码 | `grep "pattern" file` → N 处运行时调用 |

**无效证据**：数据模型存在、目录归属、编译通过、代码存在——结构代理，不是运行时证据。

### ② 方案对比

至少 2 个方案，每个含核心思路 / 优点缺点 / 实施复杂度。给出明确推荐和理由。

### ③ 详细设计

选定方案后展开：涉及模块、接口定义、数据模型变更、依赖关系。

**禁止歧义表述**：设计必须给出单一决策，禁止用"或"留多个选项。无法决策 → 走沟通规则确认，不在设计里留"或"。

| 禁止 | 正确 |
|------|------|
| "totalReviews 改为 0 或移除" | "totalReviews 字段移除" |
| "用方法 A 或方法 B 实现" | "用方法 A 实现" |

### ④ AC 定义

每条验收标准必须包含：**触发条件**、**预期行为**、**边界情况**（异常/极值/并发）、**不做**（明确排除的范围）。

### ⑤ 风险评估

| 风险 | 定义 | 处理 |
|------|------|------|
| `safe` | 纯增量，不改现有行为 | 正常确认流程 |
| `breaking` | 改现有接口/行为，需迁移消费方 | 概要中**醒目标注** |
| `destructive` | 删数据/删表/删文件/改 schema | 概要中**醒目标注** + **必须显式等用户确认** |

风险评估写入 spec 的 `## 风险评估` 节，并随拆单传到工单风险标注。

### ⑥ spec 落盘

设计定稿后写业务仓 `.studio/specs/<slug>.md`（冻结正本；studio 自研即 studio 仓 `.studio/specs/`）。frontmatter 带 `status: draft`，用户确认后转 `confirmed`。

## 位2 质量门：spec 就绪度

spec 路由拆单前过就绪度检查（定稿质量门，不单设 skill）。质量标准细则见 `~/.studio/knowledge/spec-quality-pattern.md`，每次执行前读最新版。核心维度：

| 维度 | 检查内容 | 判定 |
|------|---------|------|
| D1 结构完整 | 必要段落齐全（目标/范围/方案/AC/风险） | 缺 → fail |
| D2 AC 质量 | 每条 AC 动词开头、可判 pass/fail、无模糊词、含边界与排除项 | 模糊 → warn；无 AC → fail |
| D3 引用存活 | 引用的 spec/文件/决策真实存在且未归档；依赖概念未重新发明、无矛盾 | 失效 → warn；概念矛盾 → fail |
| D5 范围边界 | 做/不做/约束明确 | 缺 → warn |
| D6 就绪度 | 接口/数据模型/关键流程已定义，无 TBD/待定 | 低 → warn |

**收敛**：fail=0 方可路由 to-tickets；warn 汇总呈现给用户随确认一并裁决。

---

## 反模式

| 错误 | 表现 | 正确做法 |
|------|------|---------|
| 问卷式提问 | 一次抛 10 个问题 | 每轮 1-3 个最关键问题 |
| 开放式提问 | "你有什么需求？" | 给建议答案让用户确认/修改 |
| 默认假设不标注 | 悄悄替用户做决定 | 假设写进结论，显式可纠正 |
| 无限澄清 | 第 6 轮还在问细节 | 5 轮上限，剩余缺口请用户一次裁决 |
| 澄清完不固化 | 聊完直接开写代码 | 先产出结构化结论，再路由下游 |
| 只有一个方案 | 无对比直接定 | 至少 2 方案 + 推荐理由 |
| "我已经知道要做什么" | 跳过书面设计 | 未写下的设计不存在；有设计空间就必须落 spec |

## 自检

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 触发合理 | 需求确实模糊/缺四要素之一 |
| 2 | 问题聚焦 | 每轮 ≤3 个问题，且都是"必须澄清"级 |
| 3 | 建议答案 | 每个问题附建议答案，无开放式提问 |
| 4 | 停止条件 | 满足停止条件即固化，不超 5 轮 |
| 5 | 结论完整 | 结论含目标/范围/验收标准/工程归属/默认假设五要素 |
| 6 | 方案对比 | 有设计空间时 ≥2 方案 + 推荐理由 |
| 7 | 无歧义表述 | 详细设计无"或"给选项，每个决策单一 |
| 8 | 风险评估 | 方案/Phase 标注 safe/breaking/destructive |
| 9 | 位2 质量门 | spec fail=0 才路由；warn 已汇总呈现 |

## 终端状态

<HARD-GATE>
spec 含 `destructive` 风险 → 概要中醒目标注破坏性操作清单 → **必须等用户显式确认**（用户说"继续"不算，必须明确说"确认删除/确认破坏性操作"）。
</HARD-GATE>

1. **呈现概要**：目标、核心方案、关键决策、AC 概要、风险评估、位2 质量门结果。等用户确认。
2. 用户确认后：
   - spec status → `confirmed`，工单状态回写由机制承载
   - **invoke to-tickets** 拆单
