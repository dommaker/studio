# 代码审查

系统评估代码质量的方法论。多维度审查 + 多立场视角 + 法证深度分析。

---

## 集成

上游：**tdd-implement**（需要 PASS 状态的实现代码 + 原始 spec/AC 作为输入）。

输入：实现代码文件 + SDD 或轻量 PLAN + 测试文件。
产出：审查报告（通过 / 有 critical 问题需修复），以 `REVIEW_RESULT:` 协议行结尾（见"输出协议"）。

本 Skill 是开发链的**终点**。审查通过后，代码可提交。

---

## 输入契约——不做全量探索（"探索一次、工件传递"）

- 评审对象是 **SDD 文档 + 本次 diff**：拿 `git diff`（实现分支 vs 基线）对照 SDD 三层文档评审。task.md 的上下文地图已内联关键代码/签名，先读地图。
- **代码抽查即可**：对 diff 中的关键 hunks、地图标注的入口符号做定点核对；**不做全量代码库探索**（探索已在 task-planner 阶段完成，全量重扫 = 重复劳动）。
- diff 与 SDD 对不上（多出未规划的改动 / 缺少 AC 要求的改动）→ 这本身就是 finding，按严重程度记入 issues，不靠扩大探索范围解决。

---

## 硬门禁

<HARD-GATE>
在验证每条验收标准都有对应实现和通过测试之前，不得批准或提交代码。"测试通过所以完成了"不够——必须显式验证 AC 覆盖。

如果发现任何 critical 问题，审查不通过。不要提交。先修复。
</HARD-GATE>

---

## 反模式：常见借口

Agent 可能说的借口 + 逐条反驳：

| 借口 | 反驳 |
|------|------|
| "测试通过所以完成了" | 测试通过 ≠ AC 覆盖。逐条对照 AC，不依赖测试绿灯。 |
| "只是小问题，不修了" | 你的"小问题"可能是用户的"critical"。标记严重程度，让决策者判断。 |
| "能用就行，改什么" | "能用" = 功能正确 + 代码质量 + 架构一致。只满足第一个不算完成。 |
| "测试已经覆盖了" | 测试覆盖 ≠ AC 覆盖。测试可能测了 AC 未要求的行为，漏了 AC 要求的行为。 |
| "下次再修" | 下次 = 永远不。现在修。 |
| "这不在范围内" | 如果 AC 要求了，就在范围内。先查 AC 再说。 |
| "Lint 会检查的" | Lint 检查格式，不检查逻辑。review 检查逻辑。 |
| "和现有代码一致" | 现有代码 ≠ 正确代码。如果现有代码有同样的问题，标记为模式性问题。 |
| "安全问题但影响很小" | 严重程度由客观条件定义，不是你的主观判断。硬编码凭证 = critical，无例外。 |

**危险信号** — 出现以下行为时，审查不通过：
- AC 未全部有对应实现
- AC 未全部有对应测试
- 存在安全漏洞（硬编码凭证/注入风险）
- 存在门禁绕过（--no-verify/skip-ci/降阈值）
- 存在数据丢失风险

## 审查维度

维度 1（AC 覆盖）是必检项，其他维度按输入类型和变更规模自适应：

```
输入有 SDD → 全维度审查（AC 覆盖 + 质量 + 安全 + 架构 + 法证）
输入只有轻量 PLAN → AC 覆盖 + 安全性必检，其余按需（变更 > 50 行时检查）
```

未完成维度 1 不得输出审查结论。

### 并行审查

当 SDD 文件映射涉及多个独立模块时，按模块并行审查：

```
读 SDD design.md → 文件映射
依赖分析 → 哪些模块的审查独立（无交叉依赖）
独立模块 → parallel-execution 并行审查
有依赖模块 → 按依赖顺序串行审查
汇总 → 统一审查报告
```

### 1. AC 覆盖

- 每条验收标准是否有对应实现
- 每条验收标准是否有对应测试
- 测试是否覆盖正常路径、边界条件、错误处理
- 验收标准中的约束/红线是否被遵守

### 2. 代码质量

- **类型安全** — 无 `any`，泛型正确，类型推导合理
- **错误处理** — 异常不被吞掉，错误路径有处理
- **可读性** — 命名清晰，逻辑不嵌套过深
- **可维护性** — 无重复代码，遵循项目约定

### 3. 安全性

- 无硬编码凭证
- 无注入风险（SQL/命令/模板注入）
- 无权限放大
- 敏感数据正确处理

### 4. 架构一致性

- 遵循项目目录结构和模块划分
- 遵循现有导入模式
- 无重复实现（先查已有模块再新建）
- 接口设计与现有 API 风格一致

### 5. 法证分析（技术债检测）

5 类技术债模式：

| 模式 | 信号 |
|------|------|
| Fallback 滥用 | try/catch 吞异常、`\|\|` 默认值掩盖错误、silent fail |
| Hack/Workaround | 注释含 HACK/FIXME/WORKAROUND/临时、硬编码魔数 |
| 降级伪装 | 简单实现替代设计意图（如 curl 替代 e2e、skip 替代修复）|
| 门禁绕过 | --no-verify、skip-ci、降阈值、删测试让构建绿 |
| 僵尸代码 | 被注释但未删除的代码、unused import/variable 保留"以防万一" |

## 多立场视角

4 个立场提供不同审查角度，根据场景选择性使用：

| 立场 | 关注点 | 适用场景 |
|------|--------|----------|
| 质疑者 | 逻辑错误、边界遗漏、安全隐患 | 核心逻辑变更 |
| 架构师 | 架构一致性、模块耦合、接口设计 | 跨模块/新模块 |
| 执行者 | 可维护性、可读性、测试覆盖 | 日常代码变更 |
| 实用主义者 | 是否过度设计、有无更简单方案 | 新增抽象/复杂度 |

不是每次审查都需要 4 个立场。根据变更性质选择 1-2 个最相关的立场。

## 严重程度

| 级别 | 条件 | 影响 |
|------|------|------|
| critical | AC 未覆盖、安全漏洞、门禁绕过、数据丢失风险 | 审查不通过 |
| warning | 类型不安全、错误处理缺失、重复代码 | 记录，建议修复 |
| info | 风格建议、可优化点 | 仅记录 |

任何 critical 级别问题 → 审查不通过。

## 质量判断

### 好的审查

- 有具体文件:行号定位
- 区分严重程度（不是所有问题都同等重要）
- 提供修复建议（不只指出问题）
- 识别模式性问题（不只抓个案）

### 坏的审查

- 只说"这里不好"不给理由
- 所有问题都标 critical
- 纠结风格偏好（有 lint 管的事不审查）
- 忽略架构层面的问题只关注局部

## 约束

- 审查者不改代码（只提供审查意见）
- critical 问题阻断通过
- 测试执行（test/tsc/lint）由工作流处理，审查聚焦 LLM 判断维度

## 输出协议

审查报告正文之后，**必须以一行 `REVIEW_RESULT:` 协议行结尾**（系统按此行机器解析，对接 B1 reviewReport 链路）：

```
REVIEW_RESULT: {"verdict":"pass"|"reject","summary":"一句话结论","issues":[{"severity":"error"|"warn"|"info","message":"问题描述"}]}
```

- `verdict`：存在 critical 问题 → `reject`；否则 `pass`
- `severity` 映射：critical → `error`，warning → `warn`，info → `info`
- 协议行必须是输出的**最后一行**，JSON 单行、合法可解析；正文可任意长，协议行不可省略

## 自检

自检修复最多 3 轮。超过 3 轮仍未全部通过 → 停下报告，不继续循环。

审查完成后，逐项检查：

| # | 检查项 | 通过标准 | 不通过动作 |
|---|--------|---------|-----------|
| 1 | AC 逐条对照 | 每条 AC 有实现+测试+pass | 列出缺失项 |
| 2 | 无 critical 问题 | critical = 0 | 阻断，不提交 |
| 3 | 架构一致 | 无重复实现、遵循约定 | 标记需重构项 |
| 4 | 安全检查 | 无凭证/注入/权限问题 | 阻断，修复 |
| 5 | warning 全记录 | 所有已知 warning 问题已标记 | 列出遗漏项 |
| 6 | SDD status 同步 | SDD frontmatter status = `done`（无 SDD 则跳过） | 阻断，先更新 status |
| 7 | Spec status 同步 | 对应 spec frontmatter status 已更新（无 spec 则跳过） | invoke doc-manager-skill (update-spec-status) |
| 8 | 输出协议 | 报告以合法 `REVIEW_RESULT:` 单行 JSON 结尾，verdict 与 critical 计数一致 | 补上/修正协议行 |

全部通过 → 审查通过，代码可提交。自检 #7 不阻断——spec status 由 doc-manager-skill 在终端状态更新。

---

## 终端状态

<HARD-GATE>
审查通过后，必须 push 分支到远端。push 失败（如 protected branch）→ 提示用户触发工程工具链（PR + CI + merge），不得静默结束。
</HARD-GATE>

自检全部通过后：

1. **同步 spec status**：如果 SDD requirement.md 引用了 spec → **invoke doc-manager-skill**（操作类型 `update-spec-status`，输入 SDD 路径）。doc-manager-skill 负责定位 spec、更新 frontmatter status → `done`、更新 `updated` 日期。无 spec 引用 → 跳过。
2. **push 分支**：`git push origin <current-branch>`
3. **push 成功** → 流程结束
4. **push 失败**（如 `protected branch` / `GH006`）→ 醒目提示：
   > ⚠️ 推送失败：远端拒绝了当前分支的推送。
   > 请检查分支保护规则或触发工程的 CI/合并流程。不得绕过保护（--force / --no-verify）。

本 Skill 是开发链的终点。
