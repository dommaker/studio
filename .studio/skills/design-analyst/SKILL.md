# 需求分析与设计 Spec

把模糊需求变成结构化设计文档。开发链的起点。

---

## 集成

上游：无（本 Skill 是起点）。
产出：设计 Spec（`docs/specs/<slug>.md`）。
下游：**spec-review-skill**（审查 Spec 质量）。

---

## 硬门禁

<HARD-GATE>
在产出包含可验证验收标准的设计 Spec 之前，不得开始实现、编写测试、或调用任何下游 Skill。"我已经知道要做什么"不能替代书面设计。但 Step ① 可快速退出（见下方）。
</HARD-GATE>

---

## 反模式：常见借口

| 借口 | 反驳 |
|------|------|
| "我已经知道要做什么" | 未写下的设计不存在。写下来才能被审查、被验证。 |
| "这个太简单不需要设计" | 简单任务最容易漏边界。1-2 文件的改动也需要明确"做什么、不做什么"。 |
| "用户已经告诉我了" | 用户描述 ≠ 结构化设计。需要拆解为方案对比 + AC。 |
| "写设计会拖慢进度" | 修 bug 比写设计慢得多。前置投资 < 后置修复。 |
| "边做边想" | 探索式开发 = 返工的根源。先想清楚再动手。 |

**危险信号**：
- 跳过设计直接写代码
- 只有一个方案没有对比
- AC 不可测试（没有 pass/fail 条件）
- 说"先写代码再补文档"

---

## 沟通规则（贯穿全程）

分析过程中识别到需要用户决策的歧义时，反复提问确认直至达成共识。

- **事实自行查证**：能通过 grep/read/ls 查证的信息（文件是否存在、函数是否导出、接口是否定义）自行查证，不问用户
- **决策交给用户**：事实查证清楚后，怎么决策由用户确认。每个问题附推荐答案 + 理由
- **一次一个问题**：收到回复后再继续提问，不一次性抛多个问题
- **未达成共识前不执行**：在用户确认双方已达成共识前，不调用下游 skill

不属于提问范围：
- 需求文档已明确回答的
- 方案对比中已选定的
- 属于实现细节的（留给 task-planner/tdd-implement）

---

## 执行流程

### ① 理解需求 + 快速退出判断

从用户输入提取：
- **目标**：要解决什么问题
- **约束**：技术/时间/范围限制
- **验收标准**：怎样算完成

**快速退出检查**（基于已读输入判断）：

```
if 目标明确 && 约束清晰 && 方案唯一（无设计空间）:
    if 范围大（满足任一）:
        - 2+ 个独立验收标准组（不是同一功能的正反面）
        - 跨 2+ 个架构层（数据层/业务层/展示层）
        - 引入 2+ 个新概念（新实体/新 API/新 UI 模式）
        → 不跳步。输出："主观判断简单，但范围大，需完整分析"
        → 继续 Step ②
    else if 改动单一（单一模块/接口已定）:
        输出："需求明确、方案唯一、改动单一 → 跳过设计，直接实现。确认后开始？"
        → 等待用户确认 → invoke tdd-implement
    else:
        输出："需求明确、方案唯一 → 跳过设计，进入规划。确认后开始？"
        → 等待用户确认 → invoke task-planner
    终止本 Skill
```

**继续执行**的信号：
- 目标不明确，需提问澄清
- 有多种可行方案，需对比
- 涉及新模块/新架构，需探索

如果需求模糊，先提问澄清。不要假设。

### ② 第一性分析

从本质问题出发，不从当前代码推导：
- 这个问题的根本原因是什么？
- 有哪些可能的解决路径？
- 每条路径的 trade-off 是什么？

**验证要求**：分析中的每条事实性声明必须有验证证据。先 grep/read 收集证据，再写结论。禁止先写结论再补证据，禁止从结构代理推导运行时行为（"表有字段 → 能力已实现"、"在不同目录 → 行为独立"均为无效推导）。

产出中需包含**声明-证据对照表**：

| 声明 | 验证方式 | 证据摘要 |
|------|---------|---------|
| "X 能力已覆盖" | grep 消费方代码 | `grep "pattern" file` → 找到 N 处运行时调用 |
| "X 独立于 Y" | grep 查询/导入目标 | `grep "prisma\." file` → 无交叉查询 |
| "X 不存在" | grep 确认空 | 搜索范围：dir/*，结果：0 matches |

**无效证据**：数据模型存在、目录归属、编译通过、代码存在 — 这些是结构代理，不是运行时证据。

### ③ 方案对比

至少 2 个方案，每个方案包含：
- 核心思路
- 优点/缺点
- 实施复杂度

给出明确推荐和理由。

### ④ 详细设计

选定方案后展开：
- 涉及哪些模块/文件
- 接口定义（函数签名、参数、返回值）
- 数据模型变更
- 依赖关系

**禁止歧义表述**：设计文档必须给出单一决策，禁止用"或"给多个选项。如果存在多种可行方式，在方案对比（Step ③）中决策，不在详细设计中留歧义。

| 禁止 | 正确 |
|------|------|
| "totalReviews 改为 0 或移除" | "totalReviews 字段移除" |
| "用方法 A 或方法 B 实现" | "用方法 A 实现" |
| "可选：增加缓存层" | "不增加缓存层（YAGNI）" 或 "增加缓存层" |

如果确实无法决策（需用户输入），走沟通规则确认，不在详细设计中留"或"。

### ⑤ AC 定义

每条验收标准必须包含：
1. **触发条件**：什么情况下触发
2. **预期行为**：应该发生什么
3. **边界情况**：异常/极值/并发
4. **不做**：明确排除的范围

### ⑥ 风险评估

每个方案标注风险等级和破坏性：

| 风险 | 定义 | 处理 |
|------|------|------|
| `safe` | 纯增量，不改现有行为 | 正常确认流程 |
| `breaking` | 改现有接口/行为，需迁移消费方 | 概要中**醒目标注** |
| `destructive` | 删数据/删表/删文件/改 schema | 概要中**醒目标注** + **必须显式等用户确认** |

**破坏性操作清单**：
- 删除 Prisma model 或数据库表
- 删除文件或模块
- 修改共享类型定义（消费方 ≥ 3）
- 修改 API 契约（删除端点 / 改请求格式）
- 数据迁移（格式变更）

风险评估写入 spec 文档的 `## 风险评估` 节。每个 Phase/里程碑标注风险等级。

---
## 自检

自检修复最多 3 轮。超过 3 轮仍未全部通过 → 停下报告，不继续循环。不 invoke 下游。

| # | 检查项 | 通过标准 | 不通过动作 |
|---|--------|---------|-----------|
| 1 | 需求理解 | 目标 + 约束 + 验收标准明确 | 向用户提问澄清 |
| 2 | 方案对比 | 至少 2 个方案，有推荐理由 | 补充方案或说明只有一个方案的原因 |
| 3 | AC 可测试 | 每条 AC 有明确 pass/fail 条件 | 重写为可验证格式 |
| 4 | 无占位符 | 无 "TBD"/"TODO"/"待定" | 补全后再提交 |
| 5 | 范围边界 | AC 明确"不做"项 | 补充排除项 |
| 6 | 风险评估 | 每个方案/Phase 标注 `safe`/`breaking`/`destructive` | 补充风险评估节 |
| 7 | 歧义确认 | 沟通规则已执行或确认无歧义 | 按沟通规则提问确认 |
| 8 | 无歧义表述 | design.md 详细设计无"或"给选项的表述，每个决策是单一选择 | 重写为单一决策或按沟通规则确认 |

全部通过后进入终端状态。

---

## 终端状态

<HARD-GATE>
设计 Spec 完成后必须呈现概要给用户确认，不得自动进入下游。

方案含 `destructive` 风险 → 概要中醒目标注破坏性操作清单 → **必须等用户显式确认** → 确认后才路由。用户说"继续"不算显式确认破坏性方案——必须明确说"确认删除/确认破坏性操作"。

方案无 `destructive` 风险 → 呈现概要 → 用户确认后路由到下游。
</HARD-GATE>

自检全部通过后：

1. **呈现概要**：总结核心方案、关键决策、AC 概要、风险评估。等待用户确认。
2. 用户确认后：

- 方案有歧义、需审查 → **invoke spec-review-skill**
- 方案已明确、需规划 → **invoke task-planner**
- 方案已明确 + 改动单一 → **invoke tdd-implement**

路由由方案明确度自动判定，用户确认后 invoke，不跳过。
