# README 写法参考备忘

> 性质：**参考备忘，非执行票**。触发时机 = 下次 README 大改（建议等产品形态稳定一波后，如 npm 本地形态落地、方向锁定卡上线）再启用本文。2026-09-16 记。

## 现状

studio 现 README（135 行）是"架构说明书"风格：定位段 → 核心链路 ASCII 图 → 快速开始 → 结构/角色/配置/文档地图。信息准确，但**没有一张产品截图**，读者看完不知道产品长什么样、用起来是什么体验。

## 可采用的写法

### 1. 产品速览（产品页截图 + 一句话）

在 README 前部放"核心页面"：每个关键页面一张截图 + 一行说明，50/50 表格布局。读者 30 秒建立产品直觉。

候选页面：

- 频道页（@mention 派活的现场）
- WorkUnit 详情 / 评审卡（人审交互）
- PMO 项目页（进度回写）
- 监控大盘（多 agent 状态）

### 2. 演示（按场景组织，每个是可复刻的具体例子）

演示按使用场景分组，每组配截图/录屏 + "这是什么、怎么走出来的"——**具体例子，不是抽象能力描述**。

候选场景（按真实使用录制/截图）：

- 全链路：一句 `@dev` 派活 → worktree 执行 → 评审 → 自动合并（频道时间线截图串）
- 双向沟通：agent `NEED_INPUT` 挂起问人 → 人回复 → 自动续跑
- 评审打回：reviewer 拒绝 → 修复 → 再审通过

### 3. 整体结构手法

- **开头一段定定位**：粗体关键词串联，一段话说清是什么、不是什么（studio 已有，保留）。
- **对比表**：vs 直接用 agent CLI / vs 云端 coding agent 产品——"为什么不直接用 CLI"是读者第一个问题，值得一张表回答。
- **快速开始分形态**：自部署 / npm 本地两形态落地后按形态分段，每段独立完整。
- **贡献指南按杠杆分表**："想交付 X → 怎么做 → 在哪"三列表，降低外部贡献门槛。
- **兼容性/状态表**：状态列 + 一行命令列，信息密度高。

### 4. 截图资产管理

- 截图集中放 `docs/screenshots/`（如 `docs/screenshots/product-tour/`），README 只引用仓内相对路径，不用外链图床。
- 截图会过期：接受这一点，每次 README 大改**整批重截**，不零散补丁。
- **公开仓库脱敏**：截图里的频道内容、项目名、用户名必须先用演示数据铺好，不截真实工作现场。

## 不采用的

- 多语言 i18n README（studio 受众当前中文为主，YAGNI）
- Star history / 仓库指标 SVG 等运营挂件
- badge 堆叠（保持现有 3 个以内的克制）

## 启用时的动作清单

1. 确定截图页面/场景清单（先 4 页 + 2 场景，不贪多）
2. 准备演示数据（脱敏的频道/项目/WU）
3. 截图入 `docs/screenshots/product-tour/`
4. README 重排：定位段 → 产品速览 → 演示 → 对比表 → 快速开始（分形态）→ 其余保留
5. 与 docs/vision-2026.md 冲突时以 vision 为准（现有纪律保留）
