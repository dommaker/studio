# 性能基线（架构重构 Phase 0 锚点）

日期：2026-09-30　状态：基线已冻结　基线 commit：`cb42edf3`

本文记录架构重构前的 API 性能基线，作为重构前后对比的锚点。测量对象：`apps/api`（Express 4 + tsx 4.23.1 运行时转译，数据全走 FileStore）。

---

## 1. 环境

- Node.js v22.22.0，Linux x86_64。
- 机器：4 vCPU / 3.7 GB RAM（+8 GB swap，测量时 swap 已用约 4 GB）的资源受限开发机，机上同时驻留一个生产实例（127.0.0.1:3001）。**本机内存压力是冷启动数据的重要背景，换机重测需重记环境行。**
- 运行形态：与生产一致——生产 systemd 服务同样以 tsx 运行时转译启动（非构建产物），故本基线对生产形态有代表性。

## 2. 方法

- 隔离数据区：`STUDIO_HOME=$(mktemp -d)`，全程未触碰默认数据根；测量后临时目录已删除。
- 监听：`PORT=3917`（39xx 段，启动前经 `ss` 确认空闲，非 3001/13001），默认绑 127.0.0.1；`STUDIO_AUTH=none`（免登录注入 Admin，仅回环，符合 `listen-host.ts` 守卫）。
- 启动命令：`STUDIO_HOME=<tmp> PORT=3917 STUDIO_AUTH=none npx tsx apps/api/src/index.ts`（仓库根执行）。
- 冷启动：从进程启动到 `GET /health` 首次返回 200 的耗时（50ms 轮询）。run1 为全新数据区（含首启 seed/迁移），run2/run3 为同一数据区上的重启。
- 端点延迟：每端点 3 发 warmup + 50 发串行（本机回环 fetch），记录状态码分布与 p50/p95/max。数据区为空（除系统 seed 的内置 skills/默认频道外无业务数据）。
- 未测项：SSE 端到端延迟（需造事件，成本不匹配，留待 Phase 4）；写端点（本基线只覆盖只读路径）。

## 3. 冷启动

| 轮次 | 数据区 | 耗时 |
|------|--------|------|
| run1 | 全新（含首启 seed） | 24.1 s |
| run2 | 重启 | 39.2 s |
| run3 | 重启 | 47.6 s |

观察：三次测量逐轮变慢，方差大，与本机内存/swap 压力一致。启动日志显示时间主要消耗在路由注册前的串行初始化链（数据迁移 → WorkUnit 对账 → skill seed → harness bootstrap → 各后台服务动态 import），叠加 tsx 运行时转译整个模块图的开销。`/health` 要到 `server.listen` 才可用，而 listen 排在几乎全部初始化之后——冷启动耗时 ≈ 全量初始化耗时，不只框架启动。

## 5. 结论与目标值校验

对计划中的建议目标逐条校验：

- **读 p95 < 100ms：达标，目标合理。** 实测最差端点（health）p95 = 15.3ms，列表类 p95 ≤ 9.7ms，余量 6 倍以上。注意本基线是空数据区，数据量增长后 FileStore 全量扫描类端点会退化，100ms 作为重构后验收线仍有约束力。
- **写 p95 < 300ms：本基线未测写路径，无法直接校验。** 但读路径余量大、FileStore 写为本地文件追加/重写，300ms 量级不离谱，保留为目标，Phase 4 补测写路径再复核。
- **冷启动 < 3s：远不达标，目标离谱。** 实测 24–48s（tsx 运行时转译 + 串行初始化链 + 内存受限机器）。当前形态（生产也用 tsx 直跑）下 3s 不现实。建议二选一：(a) 目标改为"构建产物（node dist）冷启动 < 3s"，把转译移出运行时，并在构建形态下重测；(b) 维持 tsx 形态则定为"冷启动不劣于基线（< 60s 上限）"。重构（Phase 2 bootstrap 拆分/延迟初始化）若把非关键初始化挪到 listen 之后，`/health` 可用时间可大幅先于全量初始化完成，届时应区分"端口可服务时间"与"全量就绪时间"两个口径。

对比纪律：重构后（Phase 4）复测须用同一方法（隔离 STUDIO_HOME、同端点清单、同发数），并在文档中记录新 commit 与环境差异。

## 6. 重构后对比（Phase 4 复测）

日期：2026-10-02　复测 commit：`f0ff48c4`（Phase 0–3 全部落地后、Phase 4 改动前；Phase 4 仅新增 /api/docs 一条只读路由，对下列数字无实质影响）

环境差异：同一台 4 vCPU / 3.7 GB RAM 开发机，复测时内存压力与基线同量级（used ≈2.5 GB，swap 已用 ≈3.8 GB），Node v22.22.0 不变。方法严格复刻 §2：隔离 `STUDIO_HOME=$(mktemp -d)`、`PORT=3917`（启动前 `ss` 确认空闲）、`STUDIO_AUTH=none`、每端点 3 warmup + 50 发串行；测量后进程已杀、临时目录已删，全程未触碰默认数据根。

### 6.1 冷启动（端口可服务时间 = /health 首次 200）

| 轮次 | 数据区 | 基线 | 复测 | 变化 |
|------|--------|------|------|------|
| run1 | 全新（含首启 seed） | 24.1 s | 15.8 s | −34% |
| run2 | 重启 | 39.2 s | 10.1 s | −74% |
| run3 | 重启 | 47.6 s | 10.7 s | −78% |

口径说明：§5 已指出基线 24–48s 是「端口可服务 ≈ 全量就绪」单口径（listen 排在几乎全部初始化之后）。**重构后两口径仍未分离**：bootstrap/ 拆分保持了 listen 位于初始化链尾（migrations → reconcile → seed → harness → routes → core services → agent loops → channels → listen），warmup 任务组本就 fire-and-forget 不在链上。故上表与基线同口径可比。目标校验：「tsx 形态端口可服务 < 10s」——重启轮 10.1–10.7s 贴线未达，run1 15.8s 未达；但较基线全面大幅改善。基线 run2/run3 的 39–48s 含机器方差（当时逐轮变慢与 swap 压力正相关），复测同机同压下稳定 10–11s，改善主因归为模块图收敛（barrel 拆分/动态 import 归位减少了 tsx 运行时转译与求值面）与机器状态差异的叠加，不再细分归因。

|------|------------------|------------------|----------|
| health `GET /api/v1/health` | 9.0 / 15.3 / 16.2 | 5.7 / 9.5 / 12.9 | −38% |
| agents 列表 | 1.7 / 4.0 / 5.5 | 1.2 / 4.7 / 8.7 | +18% |
| channels 列表 | 2.0 / 5.1 / 9.0 | 1.2 / 1.7 / 2.9 | −67% |
| workunits 列表 | 1.8 / 4.2 / 10.0 | 1.2 / 2.7 / 3.5 | −36% |
| pmo 项目列表 | 1.9 / 4.4 / 8.3 | 1.4 / 2.8 / 4.6 | −36% |
| skills 列表 | 2.0 / 5.3 / 11.7 | 1.0 / 1.4 / 3.0 | −74% |
| monitoring 汇总 | 2.7 / 9.7 / 16.8 | 1.2 / 3.5 / 10.8 | −64% |
| notifications | 1.9 / 4.1 / 6.9 | 0.8 / 1.0 / 1.8 | −76% |

状态码全部 200×50，与基线一致。

### 6.3 结论

- **读 p95 < 100ms：达标且余量扩大。** 复测最差端点（health）p95 = 9.5ms，较基线最差 15.3ms 改善 38%。
- **回归 > 20% 端点：零。** 唯一正向变化是 agents 列表 p95 +18%（4.0 → 4.7ms，绝对值 +0.7ms），低于 20% 阈值且在毫秒级噪声范围（max 5.5 → 8.7 同为噪声幅度），不归因。envelope 统一包装（`{ data }` 壳）与鉴权挂载上移未造成可测开销。
- **冷启动：未达 < 10s 目标，较基线 −34%（run1）/ −74~78%（重启）。** 「端口可服务 / 全量就绪」两口径分离的架构前提（listen 前移）本轮未做，若要达标需把非关键初始化挪到 listen 之后——列为后续优化项，不在本次重构范围。
- **写 p95 < 300ms：仍未测**（本复测与基线同范围只覆盖读路径），目标保留待有写路径需求时补测。
