## 分档口径

- **先行项**：测量体系。不是优化，是尺子——先装上，其他项修完才知道有没有效。
- **P0**：人会注意到的错或等。断链静默、消息发出去 agent 十几秒才动、人闸死等没人催。

## 先行项：测量体系（#505 定案）

最小常驻版，三件事：

1. traceId 补齐三条路由路径（现状只有 @mention 路径写 WU metadata，线程回复与默认角色路径断档）。
2. 离线对齐工具：零新服务端埋点，四段（派单/等认领/执行/回执落库）事后从现有数据对齐出分布。
3. 前端 3 个埋点：点击发送、回执渲染、页面加载，复用 read-metrics 的 sink 模式落事件流。

不建 metrics 端点和观测面板（开发阶段无消费场景）。分段口径沿用「消息的旅程」六段，与六份走查报告同词汇表。

## P0：人会注意到的错或等

### P0-1 认领真唤醒（#515 定案）

- **修什么**：`workunit.created` / `status_changed`（按 claimable 过滤）改成真唤醒，复用现有 pendingWake 闩锁机制；auditor 旁路建单收口走 `WorkUnitService.create`；步间 sleep 改可中断。15s 轮询地板保留作纯兜底。
- **为什么**：实测建单到认领 8.5-12s，全是等轮询；而唤醒机制本身只要 4ms。
- **怎么算修好**：等认领 p95 < 1s；步间响应 p95 < 1s；唤醒整体失灵时最坏仍 ≤15s（复测走先行项的离线对齐工具）。

### P0-2 频道出声：评审建成与断链自愈（#516 项①②）

- **修什么**：review 子单建成即在父 WU 线程补一条系统消息「已派评审」；对账自愈补建/重派后在本频道补一条「断链已自愈」。**#159 决议 5「频道不出声」作废**（补建的单子是频道可见内容，系统自作主张改了就该说）；实现时同步更新根 CONTEXT.md「修复哲学」条目。
- **为什么**：这是走查⑥找到的两个频道静默断点——流程在推进，频道里完全没声音，人以为丢了。
- **怎么算修好**：两条 happy path 各有一条频道消息，建单与出声同一动作。

### P0-3 人闸催办与认领滞留（#516 项③⑥）

- **修什么**：in_review 待确认 30 分钟 → Web 铃铛 + 浏览器原生通知（Notification API，零配置保底）；4 小时仍未确认 → 推微信通道。WU unassigned 超 15 分钟 → 同顺序外推。**不自动确认**，人闸语义不动。
- **为什么**：人闸是主链唯一无界延迟——没有任何超时和催办，确认卡可以永远等下去。
- **怎么算修好**：两层催办按时到达，行动中心常驻兜底不受影响。

## P1：数据多了会变慢的结构性隐患

### P1-1 消息读口全量扫描改造（#514 定案，含汇总票并入的第 4 子项）

- **修什么**：统一改「指定频道 + 尾部倒扫」（复用现成 `iterateJsonlLinesBackward`，不建索引）。四个子项：
  1. `findMergeTargetWorkUnit` 全热文件读 → 倒扫；
  2. `getMessageById` 全频道扇出 → 按频道直查 + 调用点迁移；
  3. `linkWorkUnit` 已知 channelId 仍全频道扫 → 签名加 channelId；
  4. `queryMessages` 加尾部快径（limit 且无过滤时走倒扫切片），顺带覆盖分页读口（#510 嫌疑①，走查②候选 5，汇总票 #513 定案并入）。
- **为什么**：实测随热层线性恶化——222ms@2.46 万行 vs 倒扫 0.4ms，约 700 倍；分页读口 2 万行 90ms。两个坑已坐实：倒扫必须复刻去重/tombstone 口径；不可按 createdAt 时间早停（更新-append 使文件序 ≠ 时间序）。
- **怎么算修好**：2.46 万行测试数据重跑走查②基准，读口 ≤1ms 量级。

### P1-2 建单写侧 index 改 append-only（#517 项 1）

- **修什么**：`commitSnapshot` 的 index.json 全量重写改 append-only upsert 行 + 定期压实；fsync 取消，崩溃走 `rebuildIndex` 重建（events 是正本，index 只是派生物）。
- **为什么**：每次建单/状态迁移重写全量 index，随 WU 数线性变差（现在 p50 7.75ms@49 条）。
- **怎么算修好**：写侧耗时随 WU 数不再线性增长。

### P1-3 SSE replay buffer 踢出 stream chunk（#516 项⑥）

- **修什么**：500 条共享 replay buffer 不再入 stream chunk（一处过滤），关键事件独占补发窗口；stream 重连走全量 refetch 兜底。
- **为什么**：高 stream 负载下 chunk 把重连补发窗口挤没，#491 补发机制失效——重连后丢关键事件。
- **怎么算修好**：高负载下重连，关键事件补发齐全。

## 与各裁决票局部定级的差异（全局重排说明，#513 定案）

- **#517 项 2 notificationStore 局部定 P1 → 全局 P2**：它是取数纪律补齐（无 TTL/single-flight + SSE 逐条全量重拉无防抖），既非人可感知的错，也非主链结构性隐患，量级随通知数温和增长。
- **#516 未分档 → 按内容拆档**：出声两项（断链静默）与催办滞留（人可感知的等）进 P0；replay buffer（正确性隐患、触发条件窄）进 P1；冷却闸与通知渠道配置区（打磨与功能建设）进 P2。
- **#515 未分档 → P0**：等认领 8.5-12s 是主链上最刺眼的体感延迟。
- **#514 增加第 4 子项**：分页读口线性隐患（#510 嫌疑①）当时无票认领，汇总票按 #514 自己「不以当前数据量裁决」的原则并入同一项，同一套倒扫机制覆盖。
- **#505 不占 P 档**：测量体系是验收尺子，单列先行项。

## 不修（已裁决，勿再提）

每项一句话理由；候选手段全文在各走查报告（`.studio/research/2026-09-12-walk*.md`，research/* 分支）。

**#517 裁决**：
- 每消息双发 eventBus——双平面设计内行为，全内存微秒级，收敛收益≈0。
- `git ls-files` 缓存 miss——composer 打开 @ 选择器时已预热同一缓存，正常使用必命中；单仓 miss 仅 +4.4ms。`files.includes` 改 Set 同判（2099 条词表下无感）。

**走查①候选**：
- 多仓串行改并行 / 发送路径缓存预热——同属 ⑧，量级个位数 ms，放大场景（多候选仓全 miss、十万级文件大仓）当前不存在。
- @mention 链路并行化——各环节均个位数 ms，并行收益 <10ms，复杂度不值。
- 附件 8MB JSON.parse 改流式——单用户场景个位数 ms 同步段，可接受。
- 动态 import 上提模块级——ESM 缓存后仅微任务开销，非瓶颈。

**走查②候选（#514 定案时已否决）**：
- 倒扫按 createdAt 时间早停——更新-append 使文件序 ≠ 时间序，会漏。
- 合并目标指针化 / WU 索引推导 / append 侧索引——「不建索引」已定案；WU 索引语义不等价（锚点是消息时间不是 WU 活动时间）。

**走查③候选（#515 定案时已否决或覆盖）**：
- 缩短 15s idle 地板——真唤醒后地板是纯兜底，不缩。
- FileStore mtime watch 跨进程兜底——跨进程写者当前不存在，YAGNI。
- unassigned 指名单的消息唤醒扩展——主路径已被真唤醒覆盖，剩余场景边缘。

**走查④候选（嫌疑⑥不成立，扇出成本微秒级）**：
- stream chunk 合并帧——实测 1 chunk/行，收益近零。
- 服务端时间窗批处理 / chunk 负载裁剪 / 无订阅者不扇出 / 前端 rAF 合批——均属锦上添花，当前帧成本 <1ms，无修的必要。

**走查⑤**：
- 消息端点挂 apiCache——现实规模省个位数 ms 无收益，且与兜底轮询语义冲突（TTL 内喂陈旧首页）。正确修点 = P1-1 第 4 子项的尾部快径。
