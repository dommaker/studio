# 代码审查（两轴）

对 `HEAD` 与固定基点之间的 diff 做两轴审查：

- **契约轴** — 代码是否忠实兑现了来源工单的 issue/AC？
- **规范轴** — 代码是否符合本仓成文标准与气味基线？

两轴分列报告、不合并不定总级：一轴的过/不过不能掩盖另一轴。

---

## 集成

上游：**tdd-implement**（PASS 的实现代码 + 关联工单）。
输入：实现分支 diff + 来源工单（issue/AC）+ 仓内标准文档。
产出：审查报告（通过 / 有 critical 需修复），以 `REVIEW_RESULT:` 协议行结尾（见"输出协议"）。

本 Skill 是开发链的**终点**。

---

## 输入契约——不做全量探索

- 评审对象是 **工单 AC + 本次 diff**：拿 `git diff`（实现分支 vs 基线）对照工单验收标准评审。
- **代码抽查即可**：对 diff 中的关键 hunks、入口符号做定点核对；**不做全量代码库探索**。
- diff 与工单对不上（多出 AC 未要求的改动 / 缺少 AC 要求的改动）→ 这本身就是 finding，记入契约轴，不靠扩大探索范围解决。

---

## 硬门禁

<HARD-GATE>
两阶段顺序（仓 Iron Law）：**先契约轴后规范轴**——逐条对照 AC 验证实现与测试，契约轴不通过则不进规范轴，直接 reject。

在验证每条验收标准都有对应实现和通过测试之前，不得批准代码。"测试通过所以完成了"不够——必须显式验证 AC 覆盖。

发现任何 critical 问题 → 审查不通过。不提交，先修复。
</HARD-GATE>

---

## 反模式：常见借口

| 借口 | 反驳 |
|------|------|
| "测试通过所以完成了" | 测试通过 ≠ AC 覆盖。逐条对照 AC，不依赖测试绿灯。 |
| "只是小问题，不修了" | 你的"小问题"可能是用户的"critical"。标记严重程度，让决策者判断。 |
| "测试已经覆盖了" | 测试覆盖 ≠ AC 覆盖。测试可能测了 AC 未要求的行为，漏了 AC 要求的行为。 |
| "下次再修" | 下次 = 永远不。现在修。 |
| "这不在范围内" | 如果 AC 要求了，就在范围内。先查 AC 再说。 |
| "Lint 会检查的" | 工具已强制的事项两轴都跳过；review 查工具查不了的判断。 |
| "和现有代码一致" | 现有代码 ≠ 正确代码。同样的问题出现在现有代码 → 标为模式性问题。 |
| "安全问题但影响很小" | 严重程度由客观条件定义。硬编码凭证 = critical，无例外。 |

**危险信号** — 出现即审查不通过：
- AC 未全部有对应实现 / 对应测试
- 存在安全漏洞（硬编码凭证/注入风险）
- 存在门禁绕过（--no-verify/skip-ci/降阈值）
- 存在数据丢失风险

## 执行流程

### ① 定基点

用户给的基点 = commit SHA / 分支 / tag / `HEAD~5` 等。没给 → 问。

```
git rev-parse <基点>          # 先确认可解析
git diff <基点>...HEAD        # 三点，对 merge-base 比
git log <基点>..HEAD --oneline
```

基点不可解析或 diff 为空 → 在此失败，不进后续步骤。

### ② 定位契约源（spec 源定位顺序）

按序找，找到即止：

1. **WU/分支关联的工单 issue/AC**（优先）：分支名含工单号、commit message 引用（`#123`）、或上游传入的工单号 → `gh issue view <n>`（studio 自研）/ PMO 工单（业务工程）取 What to build + 验收 AC
2. 用户作为参数传入的 spec 路径
3. 业务仓 `.studio/specs/` 下与分支名/特性匹配的 spec
4. 都没有 → 问用户契约在哪；用户说没有 → 契约轴跳过，报告标注"无契约源"

### ③ 定位规范源

仓内任何成文的代码标准（`CODING_STANDARDS.md` / `CONTRIBUTING.md` / `AGENTS.md` 治理契约 / CONTEXT.md 注意事项）。

规范轴在仓内标准之上恒载**气味基线**（Fowler《重构》ch.3，仓无标准也适用），两条绑定规则：

- **仓标准覆盖基线**：仓有文可稽的标准优先；它背书的写法基线气味要压制。
- **气味恒为判断题**：每条气味是有标签的启发式（"疑似 Feature Envy"），不是硬违规；工具已强制的跳过。

逐条对照 diff（是什么 → 怎么修）：

- **Mysterious Name** — 名不副实 → 重命名；起不出诚实的名 = 设计浑浊
- **Duplicated Code** — 同一逻辑形状出现在多处 → 抽共享形状
- **Feature Envy** — 方法伸手进别人数据多过自己的 → 移到数据所在对象
- **Data Clumps** — 同几个字段总成群出现 → 捆成一个类型
- **Primitive Obsession** — 原始类型顶替领域概念 → 给它小类型
- **Repeated Switches** — 同一类型的 switch/if 级联复发 → 多态或共享 map
- **Shotgun Surgery** — 一个逻辑改动散落多文件 → 聚拢到一个模块
- **Divergent Change** — 一个文件因多个不相关原因被改 → 拆到各管一因
- **Speculative Generality** — 为没有的需求加抽象/参数/钩子 → 删，内联回真实需求
- **Message Chains** — 长 `a.b().c().d()` 导航 → 藏到首个对象的一个方法后
- **Middle Man** — 大半在转发的类 → 砍掉直接调真目标
- **Refused Bequest** — 子类无视/覆盖大半继承 → 弃继承用组合

规范轴同时覆盖仓内既定维度：

- **安全性**：无硬编码凭证、无注入（SQL/命令/模板）、无权限放大、敏感数据正确处理
- **架构一致性**：遵循目录结构与模块划分、遵循现有导入模式、无重复实现、接口风格一致
- **法证（技术债）**：Fallback 滥用（吞异常/silent fail）、Hack/Workaround（HACK/FIXME/魔数）、降级伪装（skip 替代修复）、门禁绕过、僵尸代码（注释代码/unused 保留）

### ④ 契约轴审查（Stage 1）

- 每条 AC 是否有对应实现
- 每条 AC 是否有对应测试，测试覆盖正向/边界/异常
- AC 中的约束/红线是否被遵守
- diff 是否有 AC 未要求的行为（scope creep）
- 看似实现但实现错误的 AC

每条 finding 引用 AC 原文。契约轴有 critical → 直接 reject，不进规范轴。

### ⑤ 规范轴审查（Stage 2，契约轴过后才进）

对照 ③ 的规范源 + 气味基线逐 hunk 审查。区分硬违规（成文标准违反，可为 hard）与判断题（气味恒为判断题）。

两轴都可按需拆并行 sub-agent（多独立模块时按模块拆），但两轴报告必须分列，不互相污染上下文。

### ⑥ 汇总

报告以 `## 契约轴` 与 `## 规范轴` 两节并列呈现，不合并、不跨轴重排定级。结尾一行总结：每轴 finding 数 + 各轴最重问题（如有）。

## 严重程度

| 级别 | 条件 | 影响 |
|------|------|------|
| critical | AC 未覆盖、安全漏洞、门禁绕过、数据丢失风险 | 审查不通过 |
| warning | 类型不安全、错误处理缺失、重复代码 | 记录，建议修复 |
| info | 风格建议、可优化点 | 仅记录 |

任何 critical → 审查不通过。

## 质量判断

### 好的审查

- 有具体文件:行号定位
- 区分严重程度（不是所有问题都同等重要）
- 提供修复建议（不只指出问题）
- 识别模式性问题（不只抓个案）

### 坏的审查

- 只说"这里不好"不给理由
- 所有问题都标 critical
- 纠结风格偏好（有 lint 管的事不审查）
- 忽略架构层面的问题只关注局部

## 约束

- 审查者不改代码（只提供审查意见）
- critical 问题阻断通过
- 测试执行（test/tsc/lint）由工作流处理，审查聚焦 LLM 判断维度

## 输出协议

审查报告正文之后，**必须以一行 `REVIEW_RESULT:` 协议行结尾**（系统按此行机器解析，对接 B1 reviewReport 链路）：

```
REVIEW_RESULT: {"verdict":"pass"|"reject","summary":"一句话结论","issues":[{"severity":"error"|"warn"|"info","message":"问题描述"}]}
```

- `verdict`：存在 critical 问题 → `reject`；否则 `pass`
- `severity` 映射：critical → `error`，warning → `warn`，info → `info`
- 协议行必须是输出的**最后一行**，JSON 单行、合法可解析；正文可任意长，协议行不可省略

## 自检

自检修复最多 3 轮。超过 3 轮仍未全部通过 → 停下报告，不继续循环。

| # | 检查项 | 通过标准 | 不通过动作 |
|---|--------|---------|-----------|
| 1 | 契约源定位 | 已按 ② 顺序定位工单/AC，或显式标注"无契约源" | 补定位 |
| 2 | AC 逐条对照 | 每条 AC 有实现+测试+pass | 列出缺失项 |
| 3 | 阶段顺序 | 契约轴完成后才进规范轴 | 重排审查顺序 |
| 4 | 无 critical 问题 | critical = 0 | 阻断，不提交 |
| 5 | 安全检查 | 无凭证/注入/权限问题 | 阻断，修复 |
| 6 | 两轴分列 | 报告契约轴/规范轴分节呈现，未合并定级 | 重排报告 |
| 7 | warning 全记录 | 所有已知 warning 问题已标记 | 列出遗漏项 |
| 8 | 沉淀路由 | verdict=pass 前已 invoke exploration-sediment 或显式记录 N/A（无耐久发现） | 不满足则 verdict 不得为 pass |
| 9 | 输出协议 | 报告以合法 `REVIEW_RESULT:` 单行 JSON 结尾，verdict 与 critical 计数一致 | 补上/修正协议行 |

全部通过 → 审查通过，代码可提交。

## 终端状态

<HARD-GATE>
审查通过后，必须 push 分支到远端。push 失败（如 protected branch）→ 提示用户触发工程工具链（PR + CI + merge），不得静默结束。
</HARD-GATE>

自检全部通过后：

1. **invoke exploration-sediment**：把本轮实现 + review 发现按分流清单写入对应目录 CONTEXT.md（无耐久发现则显式记录 N/A）。
2. **提交 CONTEXT.md 变更**：exploration-sediment 产生的 CONTEXT.md 改动必须 commit，且须在 push 前。
3. **push 分支**：`git push origin <current-branch>`
4. **push 成功** → 流程结束
5. **push 失败**（如 `protected branch` / `GH006`）→ 醒目提示：
   > ⚠️ 推送失败：远端拒绝了当前分支的推送。
   > 请检查分支保护规则或触发工程的 CI/合并流程。不得绕过保护（--force / --no-verify）。
