# 探索结论沉淀

把本轮调研/修复中探明的耐久事实固化到业务仓 `.studio/CONTEXT.md`——项目私有冻结文档的唯一正本，与领域术语同处一个文件（三层存储归属裁决，T1/#122）。让下一个摸这块代码的人（或 agent）不必重新探索。规则依据：根 CLAUDE.md「探索结论沉淀」节。

## 触发时机

- **任务收尾**（实现完成、测试通过后、交付回复前）：凡启动过调研（explore agent / 多路搜索 / 多文件排查）的任务必须走一遍，无例外。
- 用户明示："沉淀一下" / "写进 CONTEXT"。

## 与相邻机制的边界

| 机制 | 写哪 | 写什么 |
|------|------|--------|
| 本 skill | 业务仓 `.studio/CONTEXT.md` | 面向下一个摸代码者的耐久事实 |
| knowledge-extraction | 知识库 | 跨任务可复用的知识条目（Loop 自动触发） |
| doc-manager-skill | roadmap / spec / memory | 文档状态与进度 |

## 输入

调研报告（explore agent 结论）+ `git diff` + 用户原始诉求。

## 分流决策树（核心）

逐条过调研发现，每条落到且只落到一处。单一文件内按模块锚点组织（如 `## apps/api/src/modules/agents`），锚点下分「核心导出 / 注意事项」：

| 发现类型 | 落点 | 格式 |
|---------|------|------|
| 耐久事实（数据流 / 存储布局 / 调用链 / 鉴权分层 / 坑 / 修复教训） | 对应模块锚点的「注意事项」；结构信息放「核心导出」 | 一两句结论 + 关键文件:行号 |
| 跨模块核心知识 | 文件级（无模块锚点）的「核心导出 / 注意事项」 | 同上 |
| 未修隐患 / 已知限制 | 「注意事项」 | 「另知：…（未修）」，写清触发条件 |
| 未验证的假设 | 标「假设，未验证」或不写 | — |
| 一次性任务细节（临时 id、会话上下文、过程数据） | **不沉淀** | — |

## 维护规则（重写，非追加）

- **状态区对照 diff 增改删**：「核心导出 / 依赖关系」对照本轮 diff 做增、改、删，重写回当前真实状态——不追加新节、不留已删符号的残影。
- **自清洁**：本轮修掉的坑，同 session 删除对应「另知：…（未修）」条目；坑的教训若耐久，并入「注意事项」坑条目。

## 质量门

- 先读目标文件已有条目，不重复、不冲突。
- 每条自问：**3 个月后对没参与本轮的人还有用吗？** 没有就不写。调研报告 30 条，可能只值 3 条，宁缺毋滥。
- 写位置和结论，不贴代码实现；代码会改，结论才耐久。

## 输出

写完后在交付回复中列出沉淀清单：写了哪几条、写到哪节、其余发现为什么不写。透明可审计。

## 反模式

- 把调研报告全文搬进 CONTEXT.md（噪音淹没信号）。
- 只写一句修复叙事，漏掉调用链/坑——下次还得重新调研（修复叙事的家是 git log，不是 CONTEXT.md）。
- 给临时脚本或已删代码写文档。
- 手改根 AGENTS.md（机器维护文件）；skill 只需在仓治理文件的「可用 Skills（索引）」手写段登记一行。
