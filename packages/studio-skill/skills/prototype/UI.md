# UI 原型

在单一路由上生成**几个结构上截然不同的 UI 变体**，浮动底栏切换。用户在浏览器里翻变体，挑一个（或各偷一块），其余扔掉。

问题是逻辑/状态而非长相 → 走错分支，去 [LOGIC.md](LOGIC.md)。

## 适用信号

- 「这个页面该长什么样？」
- 「定下来之前想看几个 dashboard 方案。」
- 「设置页换个布局试试。」
- 一切用户本来要在脑子里对着三个模糊 mockup 纠结一天的场景。

## 两种子形态——强烈优先 A

UI 原型**贴着真实应用其余部分**时才好评——真实 header、真实侧栏、真实数据、真实密度。孤立的一次性路由是真空：每个变体单独看都挺好。只要有可寄宿的既有页面，默认子形态 A。原型确实没有邻近的家，才用子形态 B。

### 子形态 A——既有页面上的变体（优先）

路由已存在。变体渲染在**同一路由**上，用 `?variant=` URL search param 门控。既有数据获取、params、鉴权全保留——只换渲染子树。这是默认；没有具体理由别偏离。

原型对象还没有页面、但**自然会住在某个页面里**（dashboard 的新板块、设置页的新卡片、既有流程的新步骤）——仍是子形态 A，把变体挂进宿主页面。

### 子形态 B——新页面（最后手段）

仅当被原型物确实没有可寄宿的既有页面——全新顶层界面、或没法合理嵌入的流程。

按项目既有路由约定建**一次性路由**——别自创顶层结构。命名要一眼看出是原型（路径或文件名含 `prototype`）。同样用 `?variant=` 模式。

定 B 之前先 sanity check：真没有任何可嵌入的既有页面吗？空路由会藏住 populated 页面会暴露的设计问题。

两种子形态的浮动底栏完全相同。

## 流程

### 1. 写下问题，定 N

默认 **3 个变体**。超过 5 个就不再「截然不同」，开始变成噪音——到此封顶。

用一行写下计划，放原型位置或文件头注释：

> 「设置页三个变体，`?variant=` 切换，挂在既有 `/settings` 路由上。」

用户在场能反对、不在场也能看懂。

### 2. 生成结构截然不同的变体

逐个起草，每个变体须：

- 忠于页面用途和它拿得到的数据。
- 用项目的组件库/样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随项目）。
- 导出清晰的组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——布局不同、信息层级不同、主操作不同，不只是换色。三个微调过的卡片网格不是 UI 原型，是墙纸。两个草稿太像，就重做其中一个，显式给「不准用卡片网格」之类的约束。

### 3. 接起来

路由上建一个切换组件：

```tsx
// 伪代码——按项目框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（既有页面）：切换器以上的既有数据获取全保留，只有渲染子树随变体换。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 造浮动切换栏

屏幕底部居中、fixed 定位的小条，三件：

- **左箭头**——切上一变体（循环）。
- **变体标签**——显示当前变体 key；变体导出了名字就连名字一起，如 `B — 侧栏布局`。
- **右箭头**——切下一变体（循环）。

行为：

- 点箭头更新 URL search param（用框架路由——Next 的 `router.replace`、React Router 的 `navigate` 等），变体可分享、刷新稳定。
- 键盘 `←` `→` 同样切换。焦点在 `<input>`、`<textarea>`、`[contenteditable]` 里时不截获方向键。
- 视觉上与页面区分（如高对比胶囊 + 浅阴影），一眼看出不是被评审设计的一部分。
- 生产构建隐藏——用 `process.env.NODE_ENV !== 'production'` 或等效门控，原型万一被误合并也不会把切换栏带给用户。

切换栏做成单个共享组件，两种子形态复用，放项目共享 UI 的惯常位置。

### 5. 交出去

给出 URL（和 `?variant=` 的 key）。用户得空自己翻。最有价值的反馈通常是「我要 B 的 header 配 C 的侧栏」——那就是他们真正要的设计。

### 6. 捕获答案并清理

变体决出后，先捕获答案——哪个变体、为什么——再按 [SKILL](SKILL.md) 的产出契约处理原型：胜者折进真实代码，其余上一次性分支，不进 master：

- **子形态 A**——胜者折进既有页面；落选变体和切换栏不进 master。
- **子形态 B**——胜变体提升为正式路由；一次性路由和切换栏不进 master。

整套变体是一手来源，落一次性分支而不是进垃圾桶——变体组件和切换栏留在 master 会迅速腐烂、误导后来者。

## 反模式

- **变体只差颜色或文案。** 那是微调不是原型。真变体在结构上互相否定。
- **变体间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就背离了目的。每个变体要有扔掉整个布局的自由。
- **把变体接上真实 mutation。** 只读原型够了。变体真要写操作就指向 stub——问题是「该长什么样」，不是「后端通不通」。
- **把原型直接提生产。** 变体代码是在原型约束下写的（无测试、最少错误处理）。折进时正经重写。
