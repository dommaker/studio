# 逻辑原型

单个自包含 HTML 文件——一个**可分享的 demo**——让任何人点按钮驱动状态模型。适用问题：**业务逻辑、状态迁移、数据形状**——纸面上看着合理、只有推过真实用例才觉出不对的那类。

单文件零安装，可以递给非开发者（设计、PM、领域专家）亲手感受模型。所以它说领域语言，不说代码语言。

## 适用信号

- 「我不确定这个状态机能不能处理 X 之后接 Y 的边角。」
- 「这个数据模型到底能不能表达……的情况？」
- 「写 API 之前想先摸摸它该长什么样。」
- 一切**想按按钮、看状态变**的问题。

问题是「该长什么样」→ 走错分支了，去 [UI.md](UI.md)。

## 流程

### 1. 写下问题

写代码之前，先写下在原型什么状态模型、回答什么问题。一段话，放在 demo 顶部（可见的引言区，不只是注释）。答错问题的逻辑原型是纯浪费——把问题写明示，无论用户在场看还是事后 AFK 回来，都能核对。

### 2. 把逻辑隔离成可移植模块

真正回答问题的那段逻辑，放进一个 `<script>` 块里的纯小模块——之后能原样提出来放进真实代码库。页面是壳，一次性的；这个模块不是。

形态随问题选：

- **纯 reducer**——`(state, action) => state`。动作是离散事件、状态是单一值时适用。
- **状态机**——显式状态与迁移。「现在哪些动作合法」本身是问题的一部分时适用。
- **一组纯函数**操作普通数据类型。没有隐式当前状态、只有变换时适用。
- **方法面清晰的 class/模块**——逻辑确实要持有持续内部状态时。

选最贴合问题的形态，不是最好接页面的形态。保持纯：不碰 DOM、不碰 `document`、按钮处理不伸手进模块。页面调它，反向无流。这让原型活得过自己：问题答完，验证过的 reducer/状态机/函数组能直接提进真实模块。

### 3. 造可分享 HTML 文件

单文件，纯 HTML/CSS/JS——无框架、无打包、无 server，全部内联，双击即开、邮件发来发去也活得下来。

为非开发者写。每个标签用**领域语言**——按钮和状态读得像业务，不像 reducer。用大白话解释正在发生什么。

自上而下清晰的层次：

1. **标题 + 一句话说明**这个 demo 能探索什么（第 1 步的问题）。
2. **当前状态**——完整相关状态，渲染成可读面板（带标签的字段，不是裸 JSON dump），每次点击后重渲染让变化可见。有助于非开发者跟上时，点名刚刚变了什么。
3. **自由按钮**——一个动作一个按钮，恒可用，任何人按任意顺序戳模型。每次点击 dispatch 动作并重渲染。
4. **引导走查**——一组**场景**，一个场景一个页签。页签内是场景的大白话描述——设定什么局面、看什么——下面按序排该场景**要按的按钮**。每步是真按钮：点了执行该动作并进到下一步。开始走查先重置到已知初态，场景每次跑得一样。

选能演示别扭用例的场景——快乐路径、棘手边角、一个理应非法的操作——纸面上推不动的那些。

美观但克制：干净排版、宽松留白、一个强调色。无动画无花哨——任何东西都不得与状态和按钮抢注意力。

### 4. 交出去

把文件发过去，或当面打开。他们会自己点走查和自由探索；有价值的时刻是「等等，这不应该能发生」或「咦，我以为 X 会不一样」——那是**想法**里的 bug，正是原型全部的意义。要新动作新场景就加，原型会演化。

### 5. 捕获答案与原型

问题答完，先捕获答案，再按 [SKILL](SKILL.md) 的产出契约捕获原型。本分支的具体映射：验证过的 reducer/状态机/函数组提进真实模块（结论被吸收）；HTML 壳随一次性分支走，作为一手来源保留——单文件自包含，在分支上永远双击可重跑。

## 反模式

- **别加测试。** 需要测试的原型不再是原型。
- **别接真实数据库。** 除非问题就是持久化本身，一律内存态。
- **别泛化。** 没有「以后要支持 X 怎么办」。原型只回答一个问题。
- **别把逻辑和页面糊在一起。** 纯模块一旦引用 DOM、`document`、按钮处理，就提不走了。页面是纯模块上的薄壳。
- **别上框架/打包器/server。** 收件人双击即开的一个文件；React 应用或 dev server 直接摧毁「可分享」。
- **别把 HTML 壳带进生产。** 页面为手工点按优化。背后的逻辑模块才是值得留下的部分。
