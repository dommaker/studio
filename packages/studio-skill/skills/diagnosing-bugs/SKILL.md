# bug 诊断循环

bug = 预期已存在、无需成形，默认走快速路：不开图、不写成文单，直接落任务单走本循环（#105 2026-08-12 裁决）。

---

## 集成

上游：bug 任务单（用户报告的症状 + 环境信息）。
输入：症状描述、错误输出、可运行的代码仓。
产出：复现测试（FAIL→GREEN）+ 修复 + 防回归测试（随修复同 commit）+ 工单回写诊断结论。

边界：测试失败的三层分类（环境/依赖/代码）用 **test-diagnosis**；本 skill 管"系统行为错了"的完整诊断循环。

---

## 硬门禁

<HARD-GATE>
没有紧致反馈回路（一条已经跑过、能对本 bug 变红的命令）之前，禁止提假设、禁止改代码。
盯着代码构造理论 = 本 skill 要防的确切失败模式。
</HARD-GATE>

<HARD-GATE>
复现测试先行：先写 FAIL 的复现测试（断言用户报告的精确症状），确认变红后再修复到 GREEN。
防回归测试随修复同 commit——复现测试最小化后即为防回归测试，与修复代码同一个 commit 提交。
</HARD-GATE>

## 诊断流程

### Phase 1 — 建反馈回路（本 skill 的核心，投入要不成比例地大）

一条**紧致**的 pass/fail 信号：能在本 bug 上变红、修复后变绿。构造方式按优先级：

1. 失败测试——在够得着 bug 的接缝上写（unit / integration / e2e）
2. curl / HTTP 脚本打本地 dev server
3. CLI 调用 + fixture 输入，diff stdout
4. headless 浏览器脚本（Playwright）驱动 UI 断言
5. 一次性 harness：最小子集（单服务、mock 依赖）单函数调用触发 bug 路径
6. 二分 harness：两个已知状态之间 `git bisect run`
7. 捕获物重放 / 差分对比：真实请求/事件日志落盘后隔离重放，或同一输入跑新旧两版 diff 输出

**脱敏纪律**：展示命令、输出、捕获物之前先脱敏——密钥/令牌一律写 `<REDACTED>`；回路尽量建在环境变量上，让凭证留在环境里而不是出现在展示内容里。捕获物携带 auth header 时只引用携带信号的那几行。

**收紧回路**：更快（秒级）、信号更准（断言具体症状而非"没崩"）、更确定（pin 时间/种子/文件系统/网络）。30 秒飘忽的回路约等于没有回路。

**非确定性 bug**：目标不是干净复现，是**提高复现率**——循环触发 100 次、并行、加压、缩时间窗。50% flake 可调，1% 不可调。

**确实建不出回路**：明说。列出试过的路，向用户要：(a) 能复现的环境访问权，(b) 脱敏的捕获物（HAR/日志/core dump），或 (c) 临时生产插桩的许可。**不要**在没有回路的情况下进入假设阶段。

完成标准：能报出**一条已跑过至少一次**的命令，且它——red-capable（驱动真实 bug 路径、断言用户的确切症状）、确定、秒级、agent 可无人值守运行。

### Phase 2 — 复现 + 最小化

跑回路，确认变红的失败模式就是**用户报告的**那个（附近的另一种失败 = 修错 bug）。然后最小化：一次砍一个输入/调用方/配置/步骤，每砍一刀重跑回路，留下的每个元素都必须承重——去掉任何一个回路就变绿。最小复现 = Phase 5 防回归测试的坯子。

### Phase 3 — 假设（先列后验）

测任何一个之前，先列 **3–5 个排序假设**。每个假设必须可证伪：

> 格式：「如果 <X> 是根因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更严重」。

说不出预测的假设 = 直觉，丢弃或磨利。排序清单先给用户过一眼（领域知识能立刻重排），用户不在就按自己的排序继续，不阻塞。

### Phase 4 — 插桩定位

每个探针对应 Phase 3 的一个具体预测，**一次只改一个变量**。工具偏好：debugger/REPL > 边界定点日志 > 绝不"全量打日志再 grep"。调试日志全部带唯一前缀（如 `[DEBUG-a4f2]`），收尾一次 grep 清干净。

性能退化分支：日志通常是错的。先建基线测量（计时 harness / profiler / query plan），再二分。先测量，后修复。

### Phase 5 — 修复 + 防回归测试

有正确接缝（测试能在调用现场真实触发 bug 模式）时：

1. 把最小复现转成该接缝上的失败测试
2. 看它失败（RED）
3. 修复
4. 看它通过（GREEN）
5. 用原始（未最小化的）场景重跑 Phase 1 回路

**没有正确接缝本身就是发现**：架构让 bug 无法被锁死。记录下来，按升级触发器处理。

### Phase 6 — 收尾

- [ ] 原始场景重跑 Phase 1 回路不再复现
- [ ] 防回归测试通过（或无接缝已记录）
- [ ] 全部 `[DEBUG-...]` 插桩已清除（grep 前缀）
- [ ] 一次性 harness 已删除或移入明确标记的 debug 位置
- [ ] 被证实的那个假设写进 commit message——下一个诊断者能学到

## 升级触发器（#105 裁决）

诊断中发现**根因在需求/设计层**（预期本身错了、设计缺失接缝、规格矛盾）→ 停止修复，升级：

- 转**决策单**（单点决策）或**开图**（多决策网状，wayfinder）
- **诊断事实随工单携带**——任务单转决策单不丢上下文。升级时在工单回写：
  - 复现命令（Phase 1 回路）
  - 已排除的假设清单（各带证伪证据）
  - 定位结论（根因落在哪一层、为什么超出代码层）
- 升级可逆：已答部分沉淀为决策单内容，不浪费

## 反模式

- ❌ 没建回路就开始读代码构造理论（门禁，见上）
- ❌ 只生成一个假设就开测（锚定在第一个看似合理的想法上）
- ❌ 一次改多个变量（探针无法归因）
- ❌ 先写修复再补测试（复现测试必须先行，见硬门禁）
- ❌ 防回归测试单独拖一个 commit（必须与修复同 commit，断裂 = 回滚时丢保护）
- ❌ 修"附近的另一个失败"（复现的必须是用户报告的症状）
- ❌ 根因在需求/设计层仍就地硬修（触发升级，见上节）
